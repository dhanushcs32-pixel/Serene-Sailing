Session 15: Rudder Investigation - No Continuous-Angle Force API (Aug 11 2026):
- Checked both places force direction comes from in real Sable/Create-Aeronautics source:
  1. `BlockSubLevelLiftProvider.sable$getNormal(state)` -> returns a `Direction` (6-value axis enum only).
  2. `BlockEntityPropeller.getBlockDirection()` (propeller/fan interface, e.g. `EncasedFanBlockEntityMixin`) -> also just `Direction`.
- Finding: every force-direction hook in the engine snaps to one of 6 axis-aligned directions. Fine for a sail (only ever faces one of 6 ways) but insufficient for a rudder, which needs smooth continuous deflection, not a snap between N/E/S/W.
- Consequence for `RudderBlock`: cannot get continuous steering via `sable$getNormal()` - the return type itself can't hold a continuous angle. Only path to real steering is the same override pattern planned for sail wind: fully override `sable$contributeLiftAndDrag(...)` and skip the normal-based helper math entirely.
- Scoped implementation plan (now built, see Session 16): store a continuous angle (float, synced) on the rudder's block entity (same pattern as a valve handle/mechanical-arm angle); read that live angle from the block entity at `ctx.pos()` inside the override; compute a custom force vector via trig against local water-flow velocity (`linearVelocity`/`angularVelocity`, same inputs the sail override uses) and add directly to `linearImpulse`/`angularImpulse`.
- Confirms player-input layering (flagged as an instinct in an earlier session) is required, not optional - there is no "give me an angle" primitive to layer onto instead.
